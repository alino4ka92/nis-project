# План эксперимента

## Проверяемый вопрос

Проверяем, как ключ сортировки и размер гранул влияют на отсечение данных и стоимость восьми аналитических запросов к фиксированной выборке ClickBench.

1. При одинаковой гранулярности запросы по `CounterID` должны выигрывать от ключа с `CounterID` в начале, а запросы по `UserID` — от ключа с `UserID`.
2. При одинаковом ключе гранулы по 2048 строк могут уменьшить лишнее чтение для узких фильтров по сравнению с 8192. Одновременно растёт число индексных меток; выигрыш по времени не предполагается заранее.
3. Селективный фильтр по столбцу вне ключа может требовать чтения большей части таблицы. Малая доля подходящих строк сама по себе не гарантирует отсечение.
4. Для полного сканирования ожидаем близкое число прочитанных строк; различия времени нужно объяснять отдельно, с учётом порядка данных, сжатия и накладных расходов.

Это проверяемые ожидания, а не полученные выводы. Основное свидетельство — согласованное изменение плана, чтения и затрат.

## Сравниваемые варианты и baseline

Все четыре варианта используют MergeTree, одинаковые 105 столбцов и один входной набор. Меняются только ключ и гранулярность:

| Вариант | Таблица в `nis_skipping` | `PRIMARY KEY` и `ORDER BY` | `index_granularity` |
|---|---|---|---:|
| A, baseline | `by_counter_8192` | `(CounterID, EventDate, UserID, EventTime, WatchID)` | 8192 |
| B | `by_user_2048` | `(UserID, EventDate, CounterID, EventTime, WatchID)` | 2048 |
| C | `by_counter_2048` | `(CounterID, EventDate, UserID, EventTime, WatchID)` | 2048 |
| D | `by_user_8192` | `(UserID, EventDate, CounterID, EventTime, WatchID)` | 8192 |

В A сохранены ключ и гранулярность исходной схемы ClickBench. Общие настройки эксперимента задаются явно, поэтому A не тождественна ранее измеренной `nis_smoke.hits`.

Все четыре варианта входят в одну серию. Влияние гранулярности оцениваем по парам A/C и D/B, влияние ключа — по A/D и C/B. В каждой такой паре меняется один фактор. Сравнение A/B показывает совокупный эффект двух изменений.

У всех вариантов `index_granularity_bytes = 0`: размер гранул ограничивается числом строк, без дополнительного ограничения по байтам. Также фиксируем `min_rows_for_wide_part = 0`, `min_bytes_for_wide_part = 0`, `auto_statistics_types = ''` и `fsync_after_insert = 1`. Формат parts — Wide. Первичный ключ совпадает с ключом сортировки, дополнительных индексов и проекций нет. Обоснование настройки гранул: [документация ClickHouse](https://clickhouse.com/docs/reference/settings/merge-tree-settings/index-granularity).

К КТ-1 фиксируем конфигурации в этой таблице. Создание, загрузку и проверку таблиц реализуем к КТ-2 на командном стенде.

## Данные или нагрузки

Из всех 100 частей ClickBench отобраны строки по условию `xxHash64(toString(toUInt64(WatchID))) % 100 = 0`, все 105 колонок сохранены. Получен общий Parquet из 1 000 659 строк для всех четырёх вариантов таблицы. [Источники и контрольная сумма](../artifacts/checkpoint-1/clickbench-sample.json), [подготовка](./technical-checks.md#4-подготовка-уменьшенного-clickbench).

Отбор воспроизводим; распределения значений ожидаются близкими к исходным, редкие события могут быть представлены хуже.

### Фиксированная нагрузка

Во всех запросах вычисляются `count()` и `sum(ResolutionWidth)`. Это сохраняет одинаковую форму ответа и требует чтения данных даже в контрольном запросе без фильтра. В SQL меняется только параметр имени таблицы.

| Запрос | Фильтр и назначение | Подходящие строки по сохранённым ответам |
|---|---|---:|
| [Q01](../sql/data-skipping/queries/Q01-counter_eq.sql) | `CounterID = 251755`, узкий фильтр по первому компоненту ключа A | 1004, 0,1003% |
| [Q02](../sql/data-skipping/queries/Q02-counter_broad.sql) | `CounterID = 62`, более широкий фильтр; база для Q03 | Число уточняется до серии |
| [Q03](../sql/data-skipping/queries/Q03-counter_date.sql) | `CounterID = 62`, даты от 14 июля включительно до 16 июля 2013 года исключительно | Число уточняется до серии |
| [Q04](../sql/data-skipping/queries/Q04-user_eq.sql) | `UserID = 1313338681122956954`, узкий фильтр по первому компоненту ключа B | 307, 0,0307% |
| [Q05](../sql/data-skipping/queries/Q05-user_set.sql) | Десять `UserID` из сохранённого top-10; несколько отдельных диапазонов | 1080, 0,1079% |
| [Q06](../sql/data-skipping/queries/Q06-nonkey_adv.sql) | `AdvEngineID <> 0`, фильтр вне обоих ключей | 6371, 0,6367% |
| [Q07](../sql/data-skipping/queries/Q07-nonkey_url.sql) | `URL LIKE '%google%'`, селективный строковый фильтр вне ключей | 157, 0,0157% |
| [Q08](../sql/data-skipping/queries/Q08-full_scan.sql) | Без фильтра, контроль полного сканирования | 1 000 659, 100% |

Параметры Q04/Q05 взяты из ответа Q16, Q06 — из Q2, Q07 — из Q21 [пробного ClickBench](../artifacts/checkpoint-1/benchmark/run.tsv). Q01 опирается на [независимый эталон](../artifacts/checkpoint-1/clickbench-reference.json). Непустые ответы исходных Q37 и Q43 подтверждают присутствие `CounterID = 62` и событий в выбранном интервале; точные числа для адаптированных Q02/Q03 ещё не измерялись. Диапазон дат выборки по Q7 — 02–31 июля 2013 года.

До первой серии выполняем запросы на исходной таблице `nis_smoke.hits`, сохраняем ответы и доли подходящих строк относительно 1 000 659. Для Q03 дополнительно показываем долю внутри Q02. Ожидаемые числа из таблицы проверяем на рабочем стенде, точные числа для Q02/Q03 фиксируем впервые.

SQL адаптирован из ClickBench: параметры уточнены по выборке, проекция унифицирована, убраны сортировка и `LIMIT`. Поэтому время этих запросов не сопоставляется напрямую с опубликованными результатами ClickBench. Q01/Q05 имеют близкую долю совпадений, но разные столбцы и число диапазонов; это полезное наблюдение, а не строгое сравнение одного фактора.

До КТ-2 после профилирования фиксируем точные доли и проверяем через `EXPLAIN`, что режимы действительно различимы. Если какой-либо сценарий оказался неинформативным, изменение SQL и причина оформляются до измерений в новой версии плана. Параметры не подбираются по полученному ускорению.

## Конфигурации и план запусков

ClickHouse `26.9.27.3`, ClickBench `fa52f8524ad9`. Варианты сравниваются на одной машине при одинаковых ресурсах и настройках; результаты разных архитектур обрабатываются отдельно.

Используем два потока и лимит 3 ГиБ на запрос. Дополнительно к настройкам пробного замера задаём `optimize_move_to_prewhere = 0` и `use_skip_indexes = 0`, чтобы основной эксперимент проверял первичный индекс при одинаковой обработке столбцов. Настройки запросов сохранены в [settings.sql](../sql/data-skipping/settings.sql). Сохраняются также версия сервера, архитектура, ресурсы и фактические DDL.

Порядок работы:

1. Проверить SHA-256 Parquet и загрузку `nis_smoke.hits` по существующей инструкции участника 1. Проверить место для четырёх вариантов и временных файлов подготовки.
2. Создать и загрузить четыре таблицы, выполнить `OPTIMIZE ... FINAL` до измерений. Проверить одинаковые строки, ровно один активный part на вариант и отсутствие слияний и мутаций. Проверки и подготовка в измеряемое время не входят.
3. Сохранить эталонные ответы восьми запросов на исходной таблице. Для каждой конфигурации выполнить один прогрев каждого запроса и сверить ответ.
4. Выполнить шесть измеряемых раундов. В каждом раунде пройти запросы Q01–Q08; каждый запрос выполнить на всех четырёх вариантах. В нечётных раундах порядок вариантов A, B, C, D, в чётных — D, C, B, A. Параллельных клиентских запросов нет.
5. Сохранить ответы, `query_id`, метрики, настройки и `EXPLAIN indexes = 1` для каждой пары «запрос — вариант». Состав активных parts до и после серии должен совпасть.

Одна серия требует 32 прогрева и 192 измерений, всего 224 выполнения. Эталонные ответы, проверки и `EXPLAIN` учитываются отдельно.

Измеряем прогретый режим; файловый и страничный кеши не очищаем. В серии нет вставок, загрузок и других экспериментов. При изменении parts, ошибке запроса или несовпадении ответа серия помечается недействительной. При сильном разбросе проверяем фоновые работы и повторяем полную серию, сохраняя первоначальные данные.

Файлы запросов и применение настроек описаны в [инструкции](../sql/data-skipping/README.md). Создание и загрузка таблиц, подключение нагрузки к сборщику и измерения сравнения — задачи КТ-2.

## Метрики

Метрики собираются из `system.query_log` по уникальному `query_id`: только успешные завершения (`QueryFinish`, `is_initial_query = 1`, `exception_code = 0`). Перед выгрузкой выполняется `SYSTEM FLUSH LOGS`; журналирование запросов и `ProfileEvents` включено. Прогревы в сводку не входят.

| Метрика | Источник | Единицы |
|---|---|---|
| `elapsed_ms` | Серверная длительность, `query_duration_ms` | мс |
| `read_rows` | Число прочитанных строк, `read_rows` | строки |
| `read_bytes` | Объём прочитанных несжатых данных, `read_bytes` | байты |
| `cpu_time_us` | Сумма `UserTimeMicroseconds` и `SystemTimeMicroseconds` из `ProfileEvents` | мкс CPU |
| `memory_usage_bytes` | Память запроса, `memory_usage` | байты |

`read_rows` отличается от числа строк ответа, а `read_bytes` не измеряет физический трафик диска. CPU-время суммируется по потокам и может превышать длительность запроса. Отсутствие метрики или обоих CPU-счётчиков считается ошибкой сбора; нулевые значения допустимы.

Для объяснения отсечения сохраняются `EXPLAIN indexes = 1`, DDL и сведения об активных parts из `system.parts`. Сопоставляются выбранные гранулы и фактическое чтение.

Пробный запуск: два потока, лимит памяти 3 ГиБ, кэш ответов и кэш условий отключены, файловый кэш сохраняется. Для измерений и `EXPLAIN` задано `use_skip_indexes_on_data_read = 0`, что учитывает [особенности ClickHouse 25.9+](https://clickhouse.com/docs/reference/statements/explain#explain-plan). Настройки записываются в `run.json` и должны совпадать у сравниваемых вариантов.

[Сборщик](../scripts/checkpoint-1/measure_probe.py), [SQL выгрузки](../sql/checkpoint-1-probe-metrics.sql), [команды и результат](./technical-checks.md#7-проверка-метрик). Определения полей: [документация ClickHouse](https://clickhouse.com/docs/reference/system-tables/query_log).

## Проверка корректности

Все четыре варианта загружаются из одного Parquet с проверенным SHA-256. Сверяются число строк, количество разных `CounterID` и `UserID`, соблюдение правила отбора и агрегированные хеши полных строк с учётом дубликатов. При расхождении загрузка проверяется до начала измерений.

Проверочный запрос для `CounterID = 251755` сравнивается с независимым расчётом Python: `matched_rows = 1004`, `width_sum = 1522846`. [Проверка загрузки](../scripts/checkpoint-1/verify.py) и [сборщик](../scripts/checkpoint-1/measure_probe.py) сверяют ответ с эталоном, в том числе во всех прогревах и повторах.

Для выбранной нагрузки сохраняются SQL, параметры и ответы всех вариантов; для агрегатов готовятся независимые расчёты по Parquet. Целые числа, строки, даты и `NULL` сравниваются точно. Для конечных чисел с плавающей точкой допуск: `abs(a - b) <= 1e-9 + 1e-9 * max(abs(a), abs(b))`.

Без `ORDER BY` сравниваются наборы строк с учётом дубликатов. При равных ключах в `ORDER BY ... LIMIT` состав ответа может меняться: для отдельной проверки добавляется полный порядок либо сравнивается результат до `LIMIT`. Измеряемый SQL при этом сохраняется.

Ошибочные и неполные прогоны, дубликаты измерений и несовпадения с эталоном исключаются из анализа до исправления.

## Обработка и анализ

После прогрева выполняются шесть измеряемых повторов для каждого запроса и варианта. По пяти метрикам рассчитываются медиана, минимум и максимум; исходные записи сохраняются. Результаты разных машин, конфигураций и SQL обрабатываются отдельно. При большом разбросе проверяются фоновые операции и повторяется полная серия для всех четырёх вариантов.

В таблице сравнения приводятся медианы и диапазоны. Ускорение: `median_time_baseline / median_time_variant`; сокращение чтения: `1 - median_read_variant / median_read_baseline`. Для CPU и памяти также показываются абсолютные значения и отношения. Отношения рассчитываются при положительных знаменателях; при нулевой медиане времени ускорение отмечается как «н/д». Диапазон шести повторов показывает наблюдаемый разброс и не является доверительным интервалом.

Планируются графики времени и объёма чтения по запросам и таблица выбранных гранул из `EXPLAIN`. Пары A/C и D/B показывают влияние гранулярности при фиксированном ключе, A/D и C/B — влияние ключа при фиксированной гранулярности. Эти результаты берутся из одной серии. Результаты уменьшенного набора ограничены выбранными данными и стендом.

[Обработчик](../scripts/checkpoint-1/summarize_metrics.py) формирует `summary.tsv` с медианой, минимумом и максимумом каждой метрики. Сравнение вариантов и графики будут добавлены ко второй точке после подключения выбранной нагрузки. При времени в единицы миллисекунд небольшое отношение медиан не считается само по себе доказательством ускорения: показываем абсолютные значения, разброс и подтверждение через чтение и план.
