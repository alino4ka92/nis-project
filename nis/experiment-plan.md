## Метрики

Метрики собираются из `system.query_log` по уникальному `query_id`: только успешные завершения (`QueryFinish`, `is_initial_query = 1`, `exception_code = 0`). Перед выгрузкой выполняется `SYSTEM FLUSH LOGS`; журналирование запросов и `ProfileEvents` включено. Прогревы в сводку не входят.

| Метрика | Источник | Единицы |
|---|---|---|
| `elapsed_ms` | Серверная длительность, `query_duration_ms` | мс |
| `read_rows` | Число прочитанных строк, `read_rows` | строки |
| `read_bytes` | Объём прочитанных несжатых данных, `read_bytes` | байты |
| `cpu_time_us` | Сумма `UserTimeMicroseconds` и `SystemTimeMicroseconds` из `ProfileEvents` | мкс CPU |
| `memory_usage_bytes` | Память запроса, `memory_usage` | байты |

`read_rows` отличается от числа строк ответа, а `read_bytes` не измеряет физический трафик диска. CPU-время суммируется по потокам и может превышать длительность запроса. Отсутствие метрики или обоих CPU-счётчиков считается ошибкой сбора; нулевые значения допустимы.

Для объяснения отсечения сохраняются `EXPLAIN indexes = 1`, DDL и сведения об активных parts из `system.parts`. Сопоставляются выбранные гранулы и фактическое чтение.

Пробный запуск: два потока, лимит памяти 3 ГиБ, кэш ответов и кэш условий отключены, файловый кэш сохраняется. Для измерений и `EXPLAIN` задано `use_skip_indexes_on_data_read = 0`, что учитывает [особенности ClickHouse 25.9+](https://clickhouse.com/docs/reference/statements/explain#explain-plan). Настройки записываются в `run.json` и должны совпадать у сравниваемых вариантов.

## Проверка корректности

Оба варианта загружаются из одного Parquet с проверенным SHA-256. Сверяются число строк, количество разных `CounterID` и `UserID`, соблюдение правила отбора и агрегированные хеши полных строк с учётом дубликатов. При расхождении загрузка проверяется до начала измерений.

Проверочный запрос для `CounterID = 251755` сравнивается с независимым расчётом Python: `matched_rows = 1004`, `width_sum = 1522846`. [Проверка загрузки](../scripts/checkpoint-1/verify.py) и [сборщик](../scripts/checkpoint-1/measure_probe.py) сверяют ответ с эталоном, в том числе во всех прогревах и повторах.

После выбора нагрузки сохраняются SQL, параметры и ответы обоих вариантов; для агрегатов готовятся независимые расчёты по Parquet. Целые числа, строки, даты и `NULL` сравниваются точно. Для конечных чисел с плавающей точкой допуск: `abs(a - b) <= 1e-9 + 1e-9 * max(abs(a), abs(b))`.

Без `ORDER BY` сравниваются наборы строк с учётом дубликатов. При равных ключах в `ORDER BY ... LIMIT` состав ответа может меняться: для отдельной проверки добавляется полный порядок либо сравнивается результат до `LIMIT`. Измеряемый SQL при этом сохраняется.

Ошибочные и неполные прогоны, дубликаты измерений и несовпадения с эталоном исключаются из анализа до исправления.

## Обработка и анализ

Для каждого запроса после прогрева выполняются минимум три измеряемых повтора. По пяти метрикам рассчитываются медиана, минимум и максимум; исходные записи сохраняются. Результаты разных машин, конфигураций и SQL обрабатываются отдельно. При большом разбросе проверяются фоновые операции и повторяется полная серия для обоих вариантов.

В таблице сравнения приводятся медианы и диапазоны. Ускорение: `median_time_baseline / median_time_variant`; сокращение чтения: `1 - median_read_variant / median_read_baseline`. Для CPU и памяти также показываются абсолютные значения и отношения. Отношения рассчитываются при положительных знаменателях; при нулевой медиане времени ускорение отмечается как «н/д». Диапазон трёх повторов показывает наблюдаемый разброс.

Планируются графики времени и объёма чтения по запросам и таблица выбранных гранул из `EXPLAIN`. Если одновременно меняются ключ и гранулярность, вывод относится к конфигурациям в целом. Результаты уменьшенного набора ограничены выбранными данными и стендом.

[Обработчик](../scripts/checkpoint-1/summarize_metrics.py) формирует `summary.tsv` с медианой, минимумом и максимумом каждой метрики. Сравнение вариантов и графики будут добавлены ко второй точке после выбора конфигураций и нагрузки.
